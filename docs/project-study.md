# دراسة مشروع: تطبيق وسيط لحجز مواعيد الأطباء

> دراسة أولية قبل كتابة أي كود. التقديرات الزمنية والمالية تقريبية وتتغير بتغير النطاق.

## الحكم

**قابل للتنفيذ بالكامل.** لا يوجد في المشروع شيء يتجاوز التقنيات المتاحة اليوم — الحجز والمواقع
والإشعارات كلها مسائل محلولة. الصعوبة الحقيقية ليست في البرمجة، بل في إقناع الأطباء بالتسجيل،
وإبقاء جداولهم محدّثة، والتعامل مع من يحجز ولا يحضر.

| البند | التقدير |
|---|---|
| نسخة أولى صالحة للاستخدام (ويب) | ٥ – ٧ أسابيع |
| تكلفة التشغيل الشهرية | ٢٠ – ٥٠ دولار (عدا SMS) |
| أصعب جزء تقني | محرك المواعيد ومنع الحجز المزدوج |
| أكبر سبب لفشل أمثاله | جداول أطباء غير محدّثة |

## ١. الفكرة

التطبيق يبيع شيئاً واحداً: **موعد مؤكَّد**. المريض يعرف متى يذهب ودوره كم، والطبيب يعرف من سيأتي
اليوم. كل ما عدا ذلك إضافة لاحقة.

رحلة المريض: تحديد الموقع ← البحث ← المقارنة ← الحجز ← التثبيت ← التذكير ← الحضور ← التقييم.

**قرار مبكّر:** ابقِ التطبيق وسيط حجز فقط في نسخته الأولى. لحظة تخزين تشخيص أو تقرير طبي، تدخل في
التزامات قانونية وأمنية مختلفة تماماً — وهي غير لازمة لإثبات نجاح الفكرة.

## ٢. الأطراف الأربعة

- **المريض** — الأكثر عدداً. قد يكون كبير سن أو غير متمرس، لذا الرسائل النصية ضرورية لا رفاهية.
- **الطبيب** — مصدر الدخل. غالباً لن يفتح التطبيق يومياً؛ لا تعلّق شيئاً حرجاً على تفاعله المستمر.
- **السكرتير** — المستخدم اليومي الحقيقي. إهماله هو ما يجعل الجداول تتعارض مع الواقع.
- **إدارة المنصة** — التوثيق، إدارة المواقع والتخصصات، حل النزاعات، الأرقام.

## ٣. الميزات

### النسخة الأولى (لا تشتغل الفكرة بدونها)

**للمريض**

| الميزة | التفصيل |
|---|---|
| تسجيل برقم الهاتف | رمز تحقق عبر SMS، بلا كلمات مرور أو بريد إلكتروني |
| بحث وتصفية | محافظة ← منطقة ← تخصص ← اسم الطبيب، مع ترتيب بالأقرب/الأرخص/الأقرب موعداً |
| ملف الطبيب | صورة، تخصص دقيق، خبرة، سعر الكشف، الدوام، العنوان مع خريطة وعلامة مميزة |
| الأوقات المتاحة | عرض حقيقي لما تبقّى من فترات — لا «اتصل للاستعلام» |
| حجز الموعد | فترة أو رقم دور، تأكيد فوري أو بموافقة العيادة حسب إعداد الطبيب |
| بطاقة الحجز | رقم مرجعي، الوقت، رقم الدور، العنوان، زر اتصال بالعيادة |
| الإلغاء والتأجيل | حتى مدة يحددها الطبيب، ويُحرَّر الوقت تلقائياً لغيره |
| التذكيرات | قبل يوم، وقبل ساعتين — تخفض الغياب بشكل ملموس |
| سجل حجوزاتي | القادمة والسابقة، مع إعادة حجز بضغطة |
| حجز لفرد من العائلة | حالة شائعة جداً وتُنسى دائماً |

**للطبيب والسكرتير**

| الميزة | التفصيل |
|---|---|
| إعداد الدوام | أيام، فترات، مدة الكشف، عدد المرضى في الفترة |
| الإجازات والإغلاق | تعطيل يوم أو فترة مع إشعار تلقائي للمحجوزين |
| جدول اليوم | مرضى اليوم بالترتيب مع أرقامهم وحالة كل حجز |
| تأشير الحالة | حضر / لم يحضر / انتهى الكشف |
| إضافة حجز يدوي | لمريض حضر أو اتصل بلا تطبيق — بدونها يتعارض الجدول مع الواقع خلال أسبوع |
| تأجيل جماعي | إزاحة مواعيد اليوم دفعة واحدة مع إشعار الجميع |
| حظر مريض | بعد تكرار الغياب |
| إدارة السعر والملف | تعديل السعر، الصورة، النبذة، وسائل التواصل |
| صلاحيات السكرتير | حساب منفصل يرى الحجوزات ولا يعدّل السعر أو الملف |

**لإدارة المنصة**

| الميزة | التفصيل |
|---|---|
| توثيق الأطباء | رفع وثيقة النقابة/الشهادة ومراجعة يدوية قبل الظهور |
| إدارة المواقع | محافظات ومناطق قابلة للتعديل دون لمس الكود |
| إدارة التخصصات | قائمة مركزية مع الأسماء الشائعة لكل تخصص |
| لوحة أرقام | حجوزات اليوم، نسبة الغياب، أنشط المحافظات |
| سجل العمليات | من عدّل ماذا ومتى — ضروري عند أي نزاع |

### المرحلة الثانية (بعد أول ٢٠ – ٣٠ طبيباً)

- التقييمات — لمن حضر فعلاً فقط
- الدفع الإلكتروني وعربون صغير غير مسترد
- قائمة الانتظار مع إشعار فوري عند الإلغاء
- العيادات والمستشفيات متعددة الأطباء
- طبيب في عدة مواقع، لكل موقع جدول وسعر
- الاستشارة عن بُعد (محادثة/مكالمة مرئية)
- رفع المرفقات (تحاليل، أشعة) قبل الموعد
- تعدد اللغات مع دعم اتجاه الكتابة

### لاحقاً

الوصفة الإلكترونية · ربط الصيدليات والمختبرات · التأمين الصحي · اقتراح التخصص من الأعراض ·
الملف الطبي المتكامل.

## ٤. نظام تحديد المواقع

هرم من خمسة مستويات، يُخزَّن في جداول قابلة للتعديل من لوحة الإدارة — لا في الكود:

```
الدولة  (countries)
└── المحافظة  (governorates)          ← المستوى الأول في البحث والفلترة
    └── القضاء/المنطقة  (districts)   ← تصفية داخل المدن الكبيرة
        └── الحي/الشارع  (areas)      ← اختياري، للمدن الكثيفة
            └── العيادة  (lat/lng)    ← نقطة على الخريطة + عنوان نصي + علامة مميزة
```

**العلامة المميزة مهمة بقدر الإحداثيات.** العناوين في أغلب مدننا غير منتظمة والناس تتنقل بالمعالم،
فكل عيادة تحتاج حقلاً نصياً حراً مثل «مقابل مستشفى الجمهورية، فوق صيدلية النور» إلى جانب نقطتها
على الخريطة. سيُستخدم عملياً أكثر من الخريطة نفسها.

**طريقتان للبحث، كلتاهما ضرورية:**

1. **الاختيار اليدوي** — المريض يختار محافظته من قائمة. تعمل بلا إذن موقع وبلا إنترنت جيد، وهي
   الطريقة الافتراضية.
2. **الموقع الحالي** — «الأقرب إليّ» عبر GPS مع ترتيب بالمسافة. ميزة مساعدة فقط، لأن كثيرين
   يرفضون إذن الموقع.

تُحفظ محافظة المستخدم في ملفه بعد أول اختيار، فيفتح التطبيق مباشرة على نتائج محافظته.

**تقنياً:**

- جداول `countries → governorates → districts → areas` مترابطة، كل صف باسم عربي وإنجليزي ومعرّف ثابت.
- العيادة تحمل `area_id` للتصفية الهرمية و`lat/lng` لحساب المسافة — الاثنان معاً، لأن كلاً منهما
  يخدم بحثاً مختلفاً.
- للبحث بالمسافة: `PostGIS` مع `ST_DWithin`؛ وحتى بدونه تكفي معادلة المسافة المباشرة ما دام عدد
  العيادات بالآلاف لا الملايين.
- للخرائط: `OpenStreetMap` + `MapLibre` مجاني ويكفي؛ خرائط جوجل أدق لكنها تصبح مكلفة مع النمو.

## ٥. محرك المواعيد

إذا حجز مريضان نفس الوقت مرة واحدة أمام طبيب، تفقد الطبيب. هذا الجزء يستحق ضعف الوقت المخصص
لأي جزء آخر.

**نمطان للحجز، والسوق يحتاج كليهما:**

| النمط | كيف يعمل | يناسب |
|---|---|---|
| موعد بوقت محدد | فترات ثابتة بمدة الكشف: ٤:٠٠، ٤:٢٠، ٤:٤٠ | الأطباء الملتزمون والعيادات المنظمة |
| رقم دور ضمن فترة | «الدور ١٢ بين ٤ و٧ مساءً» بلا وقت دقيق | الواقع في أغلب العيادات |

اجعل النمط خياراً في إعدادات الطبيب. فرض المواعيد الدقيقة على طبيب لا يلتزم بها يجعل التطبيق
يبدو كاذباً، واللوم سيقع على المنصة لا على الطبيب.

**منع الحجز المزدوج:**

- **قيد فريد في قاعدة البيانات** على `(doctor_id, start_at)` للحجوزات النشطة — خط الدفاع الحقيقي.
  أي تحقق في الكود وحده سينكسر عند ضغطتين متزامنتين.
- **معاملة واحدة** تقرأ وتحجز معاً، لا قراءة ثم كتابة منفصلة.
- **حجز مؤقت** لدقيقتين أثناء الدفع، يُحرَّر تلقائياً إن لم يكتمل.
- **مصدر واحد للوقت**: تخزين بتوقيت عالمي وعرض بتوقيت العيادة.

**تفصيلة تُنسى:** لا تولّد فترات المواعيد وتخزّنها مسبقاً لسنة قادمة. خزّن *قالب الدوام*
والاستثناءات فقط، واحسب الفترات المتاحة لحظة العرض — وإلا فكل تغيير في الدوام يعني إصلاح آلاف الصفوف.

## ٦. البنية التقنية

| الطبقة | المقترح | لماذا |
|---|---|---|
| قاعدة البيانات | PostgreSQL | قيود صارمة ومعاملات موثوقة — وهو ما يحتاجه الحجز تحديداً |
| الخادم | Node + NestJS | بنية منظمة؛ Laravel بديل ممتاز لمن هو أقرب لـ PHP |
| الويب ولوحات التحكم | Next.js | سريع، يظهر في نتائج البحث، ويصلح للأدوار الأربعة |
| تطبيق الجوال | Flutter | كود واحد لأندرويد وآيفون — بعد إثبات الفكرة على الويب |
| الإشعارات | FCM + SMS | الإشعار مجاني، لكن الرسالة النصية تصل للجميع |
| الملفات | S3-compatible | صور الأطباء ووثائق التوثيق |
| الاستضافة | VPS + Docker | خادم واحد يكفي لأول آلاف المستخدمين |

البند الوحيد الذي ينمو مع الاستخدام هو الرسائل النصية. خفّفه بجعل الإشعار داخل التطبيق هو الأصل،
والرسالة النصية للتأكيد والتذكير الحرج فقط.

## ٧. المخاطر (وأغلبها لا علاقة له بالكود)

| الخطر | العلاج |
|---|---|
| **البيضة والدجاجة** — لا مرضى بلا أطباء ولا عكس | ابدأ بمحافظة واحدة وتخصصين، وسجّل ٢٠ – ٣٠ طبيباً يدوياً قبل الإطلاق |
| **جداول لا تُحدَّث** — مريض يصل لعيادة مغلقة | لوحة سكرتير بسيطة جداً، تذكير أسبوعي، وتعطيل تلقائي للأيام غير المؤكَّدة |
| **الحجز بلا حضور** | تذكيران، ثم حظر بعد ثلاث غيابات، ثم عربون رمزي لاحقاً |
| **الالتفاف على المنصة** | اجعل قيمتك في ما لا يُنسخ (أوقات محدّثة، تذكير، سجل، إعادة حجز) لا في إخفاء رقم الهاتف |
| **المسؤولية الطبية** | شروط استخدام صريحة: المنصة وسيط حجز فقط، بلا استشارة وبلا مسؤولية طبية |
| **طبيب غير حقيقي** | لا ظهور قبل مراجعة يدوية للترخيص، علامة «موثّق»، وقناة للإبلاغ |

## ٨. نموذج الربح

لا تفعّل أي نموذج ربح قبل أن يكون في المنصة أطباء يحصلون على حجوزات فعلية.

| النموذج | الحكم |
|---|---|
| **اشتراك شهري للطبيب** | الأنسب — دخل ثابت ومفهوم، ولا يحتاج بنية دفع معقدة |
| عمولة على كل حجز | عادل نظرياً، لكنه يدفع العيادة للالتفاف عليك |
| ترويج مدفوع (ظهور في أعلى نتائج المحافظة) | دخل إضافي جيد، بشرط تمييزه بوضوح كإعلان |
| رسم على المريض | الأخطر — يدفع المريض للاتصال بالعيادة مباشرة |

## ٩. خطة التنفيذ

| # | المرحلة | المدة |
|---|---|---|
| ١ | الأساس والمواقع — هيكل قاعدة البيانات وجداول المحافظات والمناطق والتخصصات ببيانات حقيقية | ٣ – ٥ أيام |
| ٢ | الحسابات والصلاحيات — تسجيل برقم الهاتف وأدوار المستخدمين الأربعة | ٤ – ٦ أيام |
| ٣ | ملفات الأطباء والبحث — الملف، التصفية بالمحافظة والتخصص، صفحة الطبيب وخريطتها | أسبوع |
| ٤ | محرك المواعيد والحجز — قوالب الدوام، حساب الفترات، الحجز والإلغاء، منع التعارض | ١٠ – ١٤ يوماً |
| ٥ | لوحة الطبيب والسكرتير — جدول اليوم، الحضور، الحجز اليدوي، الإجازات، التأجيل الجماعي | أسبوع |
| ٦ | الإشعارات والتذكيرات — داخل التطبيق ورسائل نصية ومهام مجدولة | ٣ – ٤ أيام |
| ٧ | لوحة الإدارة والتوثيق — مراجعة الأطباء، إدارة المواقع والتخصصات، الإحصاءات | ٥ – ٧ أيام |

المجموع نحو **٥ – ٧ أسابيع** لنسخة ويب كاملة قابلة للعرض على أطباء حقيقيين. تطبيق الجوال يضيف
٣ – ٤ أسابيع، ولا داعي له قبل إثبات الفكرة.

## ١٠. قرارات مطلوبة قبل البدء

هذه الخمسة تغيّر البنية فعلياً، لا شكل الواجهة فقط:

1. **أي دولة؟** — لتجهيز قائمة المحافظات والأقضية الحقيقية بدل بيانات تجريبية تُرمى لاحقاً.
2. **ويب أولاً أم جوال أولاً؟** — التوصية: الويب.
3. **موعد بوقت محدد أم رقم دور؟** — التوصية: دعم النمطين وترك الخيار للطبيب.
4. **دفع إلكتروني في النسخة الأولى؟** — التوصية: التأجيل.
5. **لغة/إطار العمل المفضّل؟** — التوصية عند عدم وجود تفضيل: Node + PostgreSQL.
